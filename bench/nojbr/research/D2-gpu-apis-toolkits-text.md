### How text pieces pair with a backend [inferred unless noted]
- CPU raster path (e.g. Skia alternative): FreeType rasterises, HarfBuzz shapes, we blit coverage masks. Simple, no shader work.
- GPU atlas path: shape with HarfBuzz, rasterise glyph bitmaps with FreeType (or swash) into an atlas, batch quads. Hinting only via FreeType (HarfBuzz has none) [read HB README].
- GPU outline path: libharfbuzz-gpu (Slug algorithm) stores glyph outlines in a buffer and rasterises in the fragment shader, resolution independent [read HB README, NEWS 14.2.0]. Limits: paint encoder rejects trees with >32767 ops, nesting >4 or PaintImage (so bitmap emoji like CBDT/sbix are not covered) [read NEWS 14.2.0 L300-ish]. Shader dialects cover GLSL/WGSL/MSL/HLSL but SPIR-V is not listed [read README], relevant for SDL_GPU (needs SPIR-V/DXIL/MSL).

## Observations for Serenity
1. HarfBuzz + FreeType over FFM is the lowest-risk text stack: both have ABI-stability statements (HarfBuzz explicit [read]) and permissive licences. FreeType needs a deliberate FTL/GPL choice [read].
2. Pure-Rust options are not directly usable from the JVM without a C shim [inferred]; rustybuzz is dead [read].
3. Of the GPU APIs, SDL_GPU has the lowest additional dependency count because SDL3 is already bound, and zlib-licenced; its cost is shader cross-compilation and the unresolved coexistence question with the current GL context [read+unknown]. wgpu-native is the most vendor-neutral WebGPU route (MIT/Apache), Dawn is Google-governed.
4. JavaFX, SWT, WLToolkit do not offer a Wayland-GPU canvas independent of a custom JDK or a different UI model [inferred from reads above].
